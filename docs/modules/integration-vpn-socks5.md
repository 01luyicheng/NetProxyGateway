# VPN + SOCKS5 集成设计（阶段 2 / v2）

本设计用于解决“手机连接到客户存在故障的无外网 WiFi 时，手机自身如何稳定访问公网（走蜂窝/云中转），同时内网访问仍走 WiFi”的问题。

阶段 1（v1）建议先交付“云端入口 SOCKS5 + 手机反向隧道 + WiFi 内网访问”，不依赖 `VpnService` 全局接管。

## 范围与前提

**本设计的目标**
- 在 WiFi 无外网或不稳定时，让手机应用的公网访问稳定走蜂窝（可经云端中继）。
- 内网访问（RFC1918 等）优先走 WiFi，避免绕行云端。

**重要前提**
- `VpnService` 输出的是 TUN 设备上的原始 IP 数据包；SOCKS5 是应用层代理协议，两者之间需要“用户态协议栈/转换层”。

## 安全基线（v2 仍必须满足）

本章节补齐 v2 在“VPN 接管 + 中转/直连并存”时容易被忽略的安全点（与 v1 的服务端约束一致，但更易出错）。

**1) 凭证与控制通道**
- 隧道/API/MQTT（如启用）均必须使用加密传输（TLS）。不得在 VPN 开启后因路由变化而出现明文回退。
- 工程师侧 SOCKS5 认证建议使用短期可撤销会话令牌；客户端不得把长期密钥写入日志、崩溃上报或可被备份导出的存储。
- MQTT 主题/权限最小化：每设备独立凭证，限制仅可发布/订阅自身主题；控制消息需携带 `message_id`、`expires_at` 与签名（或等价的消息认证机制），并做去重/时钟窗校验。

**2) anti-replay / 限流 / 封禁（必须可执行）**
- 对控制消息：实现按（`deviceId` + `message_id`）的去重缓存；允许的时钟偏移需要固定值（例如 2~5 分钟），超窗拒绝。
- 对数据面：至少按 `engineerId`、`deviceId`、`source_ip` 维度做连接数上限与带宽限速；连续鉴权失败/异常建连触发冷却与短期封禁，并生成审计事件。

**3) 目标访问约束（默认拒绝）**
- 即使在 VPN 接管模式下，仍必须维持“目标过滤的双重约束”（云端入口 + 设备端/客户端）：
	- 默认仅允许 RFC1918 IPv4 + 端口白名单走 WiFi 直连。
	- 明确拒绝：loopback、链路本地 `169.254/16`（含 `169.254.169.254`）、广播/多播等特殊地址；禁止把内网目标通过云中转外发（除非控制面显式下发 allowlist 例外并留痕）。

**4) 日志与隐私（可执行）**
- 默认仅记录分流决策所需的最小元数据（连接 id、deviceId、决策结果、失败原因）。
- 禁止记录：DNS 查询域名、HTTP/TLS payload、任何凭证或 token。
- 如需定位 VPN loop/路由问题，采用“临时调试开关 + 到期自动关闭 + 审计留痕”，并对 IP/账号字段做脱敏或哈希。

## 关键难点与推荐路线

我们不在文档中绑定具体第三方库名称；选择由 POC 结果驱动。

**推荐路线（候选 A）**：Tun2Socks（用户态协议栈）
- 责任边界：把 TUN 上的 IP 包转换为 TCP/UDP socket 流量，再交给出站连接器。
- 优点：社区成熟、实现成本低。
- 风险：JNI/原生库稳定性、UDP/DNS/IPv6 的支持差异、不同 ROM 行为差异。

**不推荐路线（候选 B）**：纯 Kotlin 自研完整 TCP/UDP 栈
- 成本与风险过高，不符合 v2 的交付节奏。

## VPN Builder 策略（Android 版本差异）

两种策略互斥，最终以 POC 选择为准：

1) **全接管（兼容性优先）**：Android 5.0+ 使用 `addRoute("0.0.0.0", 0)` 将 IPv4 全部进入 TUN，再由分流引擎决定 WiFi vs 蜂窝/云端。
2) **排除内网（性能优先）**：Android 13+ 可研究使用 `excludeRoute`（若实际行为符合预期），让明确的内网地址直接走物理 WiFi，减少进入 TUN 的包量。

说明：Builder 的 `addRoute/excludeRoute` 仅决定“哪些流量进入 TUN”，并不等同于完成“WiFi vs 蜂窝”的分流；分流仍依赖用户态协议栈/出站连接器在建立 socket 时显式绑定目标 `Network`。

## 网卡选择与防环（必须项）

**核心原则：所有由 App 主动发起的“出站连接”必须显式绑定目标网卡**，否则 Android 可能把连接错误地走到当前默认网络（通常是 WiFi）。

### 选取蜂窝/WiFi Network

不要把 `activeNetwork`（默认网络）当作“蜂窝网卡”：在 WiFi 已连接但无外网的典型场景里，默认网络通常仍是 WiFi。应通过 `NetworkCapabilities` 选择：
- 蜂窝：`TRANSPORT_CELLULAR`
- WiFi：`TRANSPORT_WIFI`

### 防 VPN 自捕获/回环

仅依赖 `addDisallowedApplication()` 不足以覆盖所有场景。必须在关键出站 socket 上调用：
- `VpnService.protect(socket)`：在 `connect()` 前对**每个**关键出站 socket 调用，确保连接云端隧道/MQTT/中继流量不被再次捕获。

补充：
- `protect()` 失败必须显式处理（重试/降级/提示），否则可能出现“控制通道被 VPN 捕获后走错网卡”，导致凭证暴露面扩大或产生回环风暴。

## DNS/UDP/IPv6 的 v2 约束

- 默认不承诺完整 UDP 转发能力；DNS 方案在 [traffic-split-engine.md](traffic-split-engine.md) 以“防泄漏优先”收敛。
- IPv6 需要在 v2 明确策略：不支持时必须在 VPN Builder 层避免截获或给出清晰降级提示。

## POC 验收清单

最小可验收目标（建议在 2~3 台不同厂商设备上验证）：

- WiFi 可连内网但无外网时：手机访问公网域名成功（走蜂窝）。
- 内网目标（RFC1918）访问稳定且低延迟（走 WiFi）。
- 无明显流量回环（VPN loop）、无持续高 CPU/异常耗电。
- MQTT 控制通道在 VPN 开启后仍稳定在线。
